## Project in one paragraph

`rom-curator` is a self-hosted web app that helps the user manage a personal ROM collection. It loads 1G1R DAT files (from Redump and No-Intro, processed through Retool — the [Fresh1G1R](https://github.com/UnluckyForSome/Fresh1G1R) project provides daily ones), lets the user pick which games they want per system, scans existing local ROM directories to detect what they already own and rename files to canonical 1G1R names, and downloads missing games individually from archive.org (not as full collection packs) either straight to the server's library or to the user's own browser. Access-restricted collections are supported via an archive.org account login. Downloaded disc-based games (PS1, Saturn, etc.) can be auto-converted to a single verified `.chd` file instead of staying as separate `.bin`/`.cue`.

The user (Camille) runs a homelab. **Phases 0–8, 10, 12 and 13 of [ROADMAP.md](./ROADMAP.md) are done — the app runs as a Docker service on the homelab and is in daily use. Phase 9 (Myrient as a secondary download source) is blocked: the service shut down on 31 March 2026. Phase 11 (display modes + ScreenScraper game info) was retired before completion (2026-11-08) — box art alone covers the need; see ROADMAP.md.**

## Stack and conventions

### Stack

| Layer          | Tech                                                                                          |
| -------------- | --------------------------------------------------------------------------------------------- |
| Frontend       | Vite + React 18 + TypeScript                                                                  |
| Styling        | Panda CSS (CSS-in-JS with build-time extraction)                                              |
| Backend        | Hono on Node 20+, TypeScript                                                                  |
| Validation     | Zod for request/response schemas                                                              |
| DAT parsing    | `fast-xml-parser`                                                                             |
| Hashing        | Hand-rolled streaming CRC32 (`apps/server/src/lib/crc32.ts`)                                  |
| Persistence    | SQLite via `better-sqlite3`, hand-rolled SQL migrations                                       |
| ZIP handling   | `fflate` (unwrapping zip-view downloads)                                                      |
| CHD conversion | `chdman` npm package (native binaries, no WASM port — runtime image is `node:20-slim`, glibc) |
| Logging        | `pino` (backend only)                                                                         |
| HTTP client    | Native `fetch` (Node 20+ has it), wrapped in `archiveFetch` for archive.org                   |
| Tests          | Vitest (frontend + backend share the same runner)                                             |
| Monorepo       | pnpm workspaces                                                                               |

### Coding conventions

- **TypeScript strict mode** everywhere (`"strict": true`, `"noUncheckedIndexedAccess": true`).
- **No `any`.** If you reach for `any`, stop and find the right type. `unknown` + narrowing is fine.
- **Zod schemas** as the source of truth for any data crossing the wire (API requests/responses, parsed DAT entries that the frontend consumes). Infer TS types from schemas: `type Game = z.infer<typeof gameSchema>`.
- **Pure functions** for parsing, matching, hashing — they must be unit-testable without a filesystem or network.
- **No global state.** Use React Query (TanStack Query) on the frontend for server state. Local UI state via `useState` / `useReducer`.
- **Filenames in kebab-case**, exported symbols in `camelCase` / `PascalCase`.
- **One responsibility per file.** If a file exports five unrelated things, split it.
- **Imports:** absolute paths from each app/package root, configured via `tsconfig.json` paths.
- **Error handling:** never swallow errors silently. Backend returns typed error envelopes; frontend surfaces them to the user.

### Commit and PR style

- Conventional commits (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`, `test:`).
- One concern per commit. If you're tempted to write "feat: stuff", split it.

## Domain background — the things you need to know

### What's a DAT file

A `.dat` file is an XML manifest describing every official ROM release for a given system. Each `<game>` entry has metadata (name, region, version) and `<rom>` children with `size`, `crc`, `md5`, `sha1`. The CRC32 is the practical identifier — fast to compute, sufficient to identify a ROM uniquely in any sane case.

There are two main authorities:

- **No-Intro** — cartridge-based systems (NES, SNES, N64, GBA, DS, Game Boy, Mega Drive, etc.).
- **Redump** — disc-based systems (PS1, PS2, GameCube, Dreamcast, Saturn, etc.).

Their DAT XML formats are slightly different — handle both. See `docs/dat-format.md`.

### What's 1G1R

"One Game One ROM" — a curated filter over a No-Intro/Redump set that keeps only one preferred release per game (typically: English, USA or EU, latest revision, licensed). The Fresh1G1R repo provides three preset filter strategies (McLean, PropeR, Hearto). The user has chosen the **PropeR** preset by default. Treat the others as optional alternatives the user can switch to later.

### Archive.org reality

This is the messy part. archive.org hosts ROM collections but inconsistently:

- Some collections store ROMs as **individual files** — direct download works.
- Some collections store the entire set as **one big ZIP** (or one per system) — archive.org lets you stream individual files from inside a ZIP, and the datanode `view_archive.php` endpoint lists and extracts entries even from restricted items.
- Most large sets are **access-restricted** — usable only with archive.org account credentials (login exchanges the password once for API keys + session cookies; the password is never stored). Restricted re-zipped collections need the `zip-view` container: the fetched bytes are a ZIP wrapping the ROM.
- Collection identifiers change, get taken down, get re-uploaded under different names — handled by re-validating suggestion candidates on every run, not by curating a list.

Strategy is documented in `docs/archive-org-strategy.md`. **Read it before writing any archive.org code.**

## Things that are out of scope (do not build)

- Multi-user support, user accounts, roles. This is a single-user homelab app.
  - Note: there is currently **no authentication of any kind** — the app is only safe on localhost or a trusted LAN. This is a consequence of the single-user/local assumption, **not** a decision that auth must never exist. Exposing the app to the internet requires adding auth (proxy-level or a single-password gate) first. See [docs/security.md](./docs/security.md).
- Cloud storage, S3, anything paid.
- Emulator integration — the app curates files, it doesn't run them.
- ScreenScraper-sourced game info (year, genre, publisher, description) and gameplay screenshots — out of scope; the phase 11 attempt was retired (2026-11-08), box art alone covers the need. (Box art itself, via libretro-thumbnails, shipped in phase 10 and stays in scope.)
- Mobile app — responsive web is fine, no native client.
- Telemetry, analytics — none.
