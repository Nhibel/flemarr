## Project in one paragraph

`rom-curator` is a self-hosted web app that helps the user manage a personal ROM collection. It loads 1G1R DAT files (from Redump and No-Intro, processed through Retool — the [Fresh1G1R](https://github.com/UnluckyForSome/Fresh1G1R) project provides daily ones), lets the user pick which games they want per system, scans existing local ROM directories to detect what they already own and rename files to canonical 1G1R names, and downloads missing games individually from archive.org (not as full collection packs).

The user (Camille) runs a homelab and intends to deploy this as a Docker service once it works. Initial scope is local dev only.

### Coding conventions

- **TypeScript strict mode** everywhere (`"strict": true`, `"noUncheckedIndexedAccess": true`).
- **No `any`.** If you reach for `any`, stop and find the right type. `unknown` + narrowing is fine.
- **Zod schemas** as the source of truth for any data crossing the wire (API requests/responses, parsed DAT entries that the frontend consumes). Infer TS types from schemas: `type Game = z.infer<typeof gameSchema>`.
- **Pure functions** for parsing, matching, hashing — they must be unit-testable without a filesystem or network.
- **No global state.** Use React Query (TanStack Query) on the frontend for server state. Local UI state via `useState` / `useReducer`.
- **Filenames in kebab-case**, exported symbols in `camelCase` / `PascalCase`.
- **One responsibility per file.** If a file exports five unrelated things, split it.
- **Imports:** absolute paths from each app/package root, configured via `tsconfig.json` paths.
- **Error handling:** never swallow errors silently. Backend returns typed error envelopes; frontend surfaces them to the user.

### Commit and PR style

- Conventional commits (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`, `test:`).
- One concern per commit. If you're tempted to write "feat: stuff", split it.

## Domain background — the things you need to know

### What's a DAT file

A `.dat` file is an XML manifest describing every official ROM release for a given system. Each `<game>` entry has metadata (name, region, version) and `<rom>` children with `size`, `crc`, `md5`, `sha1`. The CRC32 is the practical identifier — fast to compute, sufficient to identify a ROM uniquely in any sane case.

There are two main authorities:
- **No-Intro** — cartridge-based systems (NES, SNES, N64, GBA, DS, Game Boy, Mega Drive, etc.).
- **Redump** — disc-based systems (PS1, PS2, GameCube, Dreamcast, Saturn, etc.).

Their DAT XML formats are slightly different — handle both. See `docs/dat-format.md`.

### What's 1G1R

"One Game One ROM" — a curated filter over a No-Intro/Redump set that keeps only one preferred release per game (typically: English, USA or EU, latest revision, licensed). The Fresh1G1R repo provides three preset filter strategies (McLean, PropeR, Hearto). The user has chosen the **PropeR** preset by default. Treat the others as optional alternatives the user can switch to later.

### Archive.org reality

This is the messy part. archive.org hosts ROM collections but inconsistently:
- Some collections store ROMs as **individual files** — direct download works.
- Some collections store the entire set as **one big ZIP** — but archive.org lets you stream individual files from inside the ZIP via a special URL pattern.
- Collection identifiers change, get taken down, get re-uploaded under different names.

Strategy is documented in `docs/archive-org-strategy.md`. **Read it before writing any archive.org code.**
